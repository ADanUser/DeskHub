# Архитектура DeskHub

## Архитектурный стиль

Проект построен на Django и использует паттерн MVT:

- Model — описание данных и связей в БД;
- View — обработка HTTP-запросов, бизнес-логика и выбор шаблона/JSON-ответа;
- Template — HTML-представление данных.

В классическом MVC контроллер отдельно управляет действиями пользователя, а во Django роль контроллера частично выполняет сам фреймворк через URL routing, middleware и view-функции.

## Структура проекта

```text
DeskHub/
├── deskhub/       # настройки проекта, urls, middleware, wsgi/asgi
├── users/         # пользователи, формы, auth views
├── venues/        # города, коворкинги, слоты, поиск, API площадок
├── bookings/      # корзина, бронирования, checkout, API броней
├── templates/     # общие шаблоны
├── static/        # CSS
├── media/         # загруженные изображения
├── manage.py
├── README.md
├── API.md
└── ARCHITECTURE.md
```

## Роли приложений

### `deskhub`

Содержит глобальную конфигурацию:

- `settings.py` — настройки Django, БД, middleware, static/media, auth redirects;
- `urls.py` — корневая маршрутизация;
- `middleware.py` — кастомные middleware.

### `users`

Отвечает за пользователей:

- модель `User`, наследуется от `AbstractUser`;
- форма регистрации `CustomUserCreationForm`;
- views: `register`, `login_view`, `logout_view`;
- URL: `/users/register/`, `/users/login/`, `/users/logout/`.

### `venues`

Отвечает за каталог:

- модели `City`, `Venue`, `Slot`;
- главная страница;
- поиск;
- детальная страница коворкинга;
- API списка и деталей коворкингов.

### `bookings`

Отвечает за покупательский сценарий:

- модель `Booking`;
- корзина в сессии;
- оформление бронирования;
- личный кабинет;
- отмена брони;
- API бронирований текущего пользователя.

## Middleware

В проекте есть два кастомных middleware.

### `RequestLoggingMiddleware`

Логирует метод, путь и время обработки запроса:

```text
Request: GET /search/ | Time: 0.0123s
```

Для junior-собеседования можно сказать: middleware — это слой между запросом и view, который может выполнить код до и после обработки запроса.

### `CartMiddleware`

Берёт корзину из сессии и добавляет к `request` поля:

- `request.cart_count`;
- `request.cart_ids`.

Это нужно, чтобы в шаблонах можно было показать количество товаров в корзине и отметить кнопку «В корзине».

## Поток запроса

Пример поиска коворкинга:

1. Пользователь открывает `/search/?city=1&date=2026-05-22&resource_type=workplace`.
2. Django находит URL в `venues/urls.py`.
3. Вызывается view `venues.views.search`.
4. View читает GET-параметры.
5. Через ORM фильтруются `Venue` и связанные `Slot`.
6. Подключается пагинация.
7. Рендерится шаблон `venues/search_results.html`.

## Поток бронирования

1. Пользователь выбирает слот на странице коворкинга.
2. JavaScript отправляет AJAX-запрос на `/bookings/cart/toggle/<slot_id>/`.
3. ID слота добавляется в `request.session['cart']`.
4. На странице корзины показываются выбранные слоты и итоговая цена.
5. При checkout пользователь должен быть авторизован.
6. В `transaction.atomic()` слоты блокируются через `select_for_update()`.
7. Проверяется, что слоты существуют и доступны.
8. Создаются записи `Booking`.
9. У слотов `is_available` становится `False`.
10. Корзина очищается.

## Что важно подчеркнуть на собеседовании

- Проект разделён по ответственности, а не свален в один файл.
- Корзина не хранится в БД, потому что это временное состояние пользователя.
- Бронирование хранится в БД, потому что это бизнес-сущность.
- Checkout защищён транзакцией, потому что это критичный участок.
- API сделано через `JsonResponse`, потому что для простого проекта не обязательно подключать DRF.
