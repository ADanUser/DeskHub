# Модели и база данных

## Общая схема данных

Основные сущности:

- `User` — пользователь системы;
- `City` — город;
- `Venue` — коворкинг;
- `Slot` — доступный временной слот;
- `Booking` — бронирование слота пользователем.

## `User`

Файл: `users/models.py`

```python
class User(AbstractUser):
    pass
```

Модель наследуется от `AbstractUser`. Сейчас она не добавляет новых полей, но проект уже готов к расширению пользовательской модели.

Почему это полезно:

- можно позже добавить телефон, аватар, роль, профиль;
- лучше сразу использовать кастомную модель пользователя, чем потом мигрировать со стандартной `auth.User`;
- в `settings.py` задано `AUTH_USER_MODEL = 'users.User'`.

## `City`

Файл: `venues/models.py`

Поля:

- `name` — название города, уникальное;
- `slug` — уникальный slug.

Связь:

- один город содержит много коворкингов.

Тип связи:

```python
City 1 -> N Venue
```

## `Venue`

Файл: `venues/models.py`

Поля:

- `name` — название коворкинга;
- `city` — внешний ключ на город;
- `address` — адрес;
- `description` — описание;
- `image` — изображение.

Связи:

- `Venue` принадлежит одному `City`;
- `Venue` имеет много `Slot`.

В коде:

```python
city = models.ForeignKey(City, on_delete=models.CASCADE, related_name='venues')
```

`on_delete=models.CASCADE` значит: если удалить город, связанные коворкинги тоже удалятся.

`related_name='venues'` позволяет получить коворкинги города так:

```python
city.venues.all()
```

## `Slot`

Файл: `venues/models.py`

Поля:

- `venue` — коворкинг;
- `resource_type` — тип ресурса: рабочее место или переговорная;
- `date` — дата;
- `start_time` — время начала;
- `end_time` — время окончания;
- `price` — цена;
- `is_available` — доступен ли слот.

Типы ресурсов:

- `workplace` — рабочее место;
- `meeting_room` — переговорная комната.

`Slot` — это конкретное предложение для бронирования: место в конкретном коворкинге на конкретную дату и время.

## `Booking`

Файл: `bookings/models.py`

Поля:

- `user` — пользователь, который сделал бронь;
- `slot` — забронированный слот;
- `status` — статус бронирования;
- `created_at` — дата создания.

Связь пользователя:

```python
user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name='bookings')
```

Один пользователь может иметь много бронирований.

Связь слота:

```python
slot = models.OneToOneField(Slot, on_delete=models.CASCADE, related_name='booking')
```

Один слот может быть связан только с одним бронированием. Это защищает бизнес-логику: один временной слот нельзя забронировать дважды.

## Статусы бронирования

- `pending` — ожидает подтверждения;
- `confirmed` — подтверждена;
- `rejected` — отклонена;
- `canceled` — отменена;
- `completed` — завершена.

## Почему есть и `OneToOneField`, и `is_available`

`OneToOneField` на уровне БД не даёт создать две брони на один слот.  
`is_available` упрощает фильтрацию свободных слотов в интерфейсе и API.

На собеседовании можно сказать:

«`OneToOneField` — это защита целостности данных, а `is_available` — удобный флаг для быстрых выборок свободных слотов. В идеале при развитии проекта нужно внимательно следить, чтобы эти два источника состояния не расходились.»

## Транзакции

В checkout используется:

```python
with transaction.atomic():
    slots = Slot.objects.filter(id__in=cart).select_for_update()
```

Зачем:

- `transaction.atomic()` делает операции единым блоком;
- если внутри ошибка, изменения откатятся;
- `select_for_update()` блокирует выбранные строки до конца транзакции;
- это снижает риск двойного бронирования при одновременных запросах.

## Оптимизация ORM

В проекте используется `select_related()`:

```python
Venue.objects.select_related('city')
Booking.objects.filter(user=request.user).select_related('slot', 'slot__venue')
```

`select_related()` делает SQL JOIN и заранее подгружает связанные объекты. Это помогает избежать N+1 query problem.

## Что такое N+1

N+1 — ситуация, когда приложение делает один запрос за списком объектов, а потом ещё N запросов за связанными данными каждого объекта.

Пример плохого сценария:

1. Получили 100 коворкингов.
2. Для каждого отдельно запросили город.
3. Итого 101 запрос.

`select_related('city')` позволяет получить всё одним JOIN-запросом.
