# Пользовательские сценарии

## Сценарий 1: поиск коворкинга

1. Пользователь заходит на главную страницу `/`.
2. Видит форму выбора города.
3. Выбирает город и нажимает «Найти».
4. Попадает на `/search/?city=<id>`.
5. Система показывает список коворкингов.
6. Пользователь может дополнительно фильтровать по дате и типу места.

Что происходит в коде:

- `venues.views.index` отдаёт главную страницу;
- `venues.views.search` обрабатывает фильтры;
- данные берутся из моделей `City`, `Venue`, `Slot`;
- результат выводится через `venues/search_results.html`.

## Сценарий 2: просмотр коворкинга

1. Пользователь нажимает «Подробнее».
2. Открывается страница `/<venue_id>/`.
3. Система показывает название, город, адрес, описание и свободные слоты.
4. Пользователь может фильтровать слоты по дате и типу.

Что происходит в коде:

- `venues.views.venue_detail`;
- `get_object_or_404()` получает коворкинг;
- слоты фильтруются по `venue`, `is_available=True`, `date`, `resource_type`;
- используется пагинация по 9 слотов.

## Сценарий 3: добавление слота в корзину

1. Пользователь нажимает «В корзину».
2. JavaScript отправляет AJAX-запрос на `/bookings/cart/toggle/<slot_id>/`.
3. View `toggle_cart` проверяет, есть ли ID слота в сессии.
4. Если ID нет — добавляет.
5. Если ID уже есть — удаляет.
6. Возвращается JSON с действием и новым количеством товаров.
7. Кнопка и бейдж корзины обновляются без перезагрузки страницы.

Почему корзина хранится в сессии:

- это временное состояние;
- не нужно создавать таблицу корзины для простого проекта;
- сессия уже привязана к пользователю/браузеру.

## Сценарий 4: оформление бронирования

1. Пользователь открывает корзину `/bookings/cart/`.
2. Видит выбранные слоты и итоговую цену.
3. Нажимает checkout.
4. Если пользователь не авторизован, `@login_required` отправит его на страницу входа.
5. Если авторизован, начинается транзакция.
6. Система проверяет, существуют ли слоты.
7. Система проверяет, доступны ли слоты.
8. Для каждого слота создаётся `Booking`.
9. Каждый слот помечается как недоступный.
10. Корзина очищается.
11. Пользователь перенаправляется в «Мои бронирования».

Важный момент:

Checkout использует `transaction.atomic()` и `select_for_update()`. Это нужно, чтобы два пользователя не смогли одновременно успешно забронировать один и тот же слот.

## Сценарий 5: просмотр моих бронирований

1. Авторизованный пользователь открывает `/bookings/my-bookings/`.
2. Система выбирает брони только текущего пользователя.
3. Брони сортируются по `created_at` от новых к старым.
4. В шаблоне отображаются детали слота и статус бронирования.

Что происходит в коде:

```python
Booking.objects.filter(user=request.user).select_related('slot', 'slot__venue').order_by('-created_at')
```

Так пользователь не может увидеть чужие бронирования через интерфейс.

## Сценарий 6: отмена бронирования

1. Пользователь нажимает отмену брони.
2. Запрос идёт на `/bookings/cancel/<booking_id>/`.
3. Система ищет бронь по `id` и `user=request.user`.
4. Если бронь принадлежит другому пользователю, она не будет найдена.
5. Если статус `pending` или `confirmed`, бронь переводится в `canceled`.
6. Слот снова становится доступным.

## Сценарий 7: администратор

Администратор через `/admin/` может:

- создавать города;
- создавать коворкинги;
- добавлять слоты;
- фильтровать слоты;
- менять статусы бронирований;
- подтверждать, отклонять и отменять брони admin actions.

## Что можно сказать про UX

«Я сделал базовый пользовательский путь: поиск → просмотр площадки → добавление слота в корзину → оформление бронирования → просмотр истории. Для удобства добавление в корзину работает через AJAX, поэтому страница не перезагружается.»
