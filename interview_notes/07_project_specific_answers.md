# Ответы от лица автора проекта

## Рассказ о проекте на 1 минуту

Я разработал DeskHub — web-приложение для поиска и бронирования коворкингов. Пользователь может выбрать город, найти площадку, посмотреть доступные слоты по дате и типу ресурса, добавить слот в корзину и оформить бронирование. Проект написан на Django, использует PostgreSQL, Django Templates, Bootstrap и сессии. Я разделил логику на приложения `users`, `venues` и `bookings`, добавил авторизацию, админку, JSON API и транзакционное оформление бронирований.

## Рассказ о проекте на 2–3 минуты

DeskHub — это платформа для бронирования рабочих мест и переговорных комнат в коворкингах. Я выбрал Django, потому что он хорошо подходит для CRUD-приложений и сразу даёт ORM, миграции, шаблоны, сессии, авторизацию и админ-панель.

Проект разделён на несколько Django apps. В `users` находится кастомная модель пользователя на основе `AbstractUser`, регистрация, вход и выход. В `venues` находятся модели городов, коворкингов и слотов, а также поиск, фильтрация и API по коворкингам. В `bookings` находится корзина, checkout, модель бронирования, отмена брони и API бронирований пользователя.

Корзина хранится в сессии как список ID слотов, потому что это временное состояние. А само бронирование хранится в базе данных, потому что это уже важная бизнес-сущность. При checkout я использую `transaction.atomic()` и `select_for_update()`, чтобы операции создания брони и изменения доступности слота выполнялись атомарно и чтобы уменьшить риск двойного бронирования.

Также я использовал `select_related()` для оптимизации запросов, пагинацию для списков, `JsonResponse` для простого API и Django Admin для управления данными.

## Почему такая структура проекта?

Я разделил проект по бизнес-ответственности:

- пользователи отдельно;
- коворкинги и слоты отдельно;
- бронирования отдельно.

Так проще поддерживать код: если нужно изменить поиск, я иду в `venues`; если checkout — в `bookings`; если регистрацию — в `users`.

## Почему кастомная модель пользователя, если в ней нет полей?

Я сделал `User(AbstractUser)` заранее, потому что поменять модель пользователя после начала проекта сложно. Даже если сейчас дополнительных полей нет, потом можно добавить телефон, аватар, роль или профиль без болезненной миграции со стандартной модели.

## Почему корзина в сессии?

Корзина — временное состояние до оформления бронирования. Для такого проекта не обязательно хранить её в отдельной таблице. Сессия позволяет хранить список ID слотов для конкретного пользователя или браузера, а при checkout эти ID превращаются в полноценные записи `Booking`.

## Почему слот связан с бронью через `OneToOneField`?

Потому что один конкретный временной слот не должен быть забронирован несколькими пользователями. `OneToOneField` помогает обеспечить это на уровне модели и базы данных.

## Почему есть поле `is_available`?

Оно упрощает фильтрацию свободных слотов в поиске, карточке коворкинга и API. Но я понимаю, что при таком подходе важно поддерживать согласованность между `is_available` и наличием бронирования.

## Почему checkout через транзакцию?

Checkout — критичный участок. Нужно создать бронь, изменить слот и очистить корзину согласованно. Если произойдёт ошибка, транзакция откатит изменения. `select_for_update()` дополнительно блокирует выбранные строки слотов на время транзакции.

## Как реализована защита от чужих бронирований?

В личном кабинете и API брони фильтруются по `request.user`. При отмене бронирования объект ищется так:

```python
get_object_or_404(Booking, id=booking_id, user=request.user)
```

То есть пользователь может отменить только свою бронь.

## Почему API без DRF?

Я хотел показать базовую работу Django без лишних зависимостей. API в проекте простое, поэтому `JsonResponse` достаточно. Если бы проект развивался как полноценный backend для SPA или мобильного приложения, я бы подключил Django REST Framework.

## Какие есть слабые места?

- мало автоматических тестов;
- нет Docker и CI/CD;
- нет полноценной роли владельца коворкинга;
- нет оплаты;
- нет email/SMS-уведомлений;
- API простое и без DRF;
- можно добавить индексы для частых фильтров;
- можно сильнее нормализовать бизнес-логику в сервисный слой.
